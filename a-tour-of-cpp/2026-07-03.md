## Standard-Library Components

The STL contains a variety of components. The main criteria for including a class in the library were that:
* It could be helpful to almost every C++ programmer.
* It could be provided in a general form that did not add significant overhead compared to a simpler version of the same facility.
* Simple uses should be easy to learn.

## Standard-Library Organization

### Namespaces

The standard library is defined in the `std` namespace. People will usually use it with:

```cpp
#include <string>
using namespace std;
```

There are plenty of sub-namespaces:
* `std::chrono`
* `std::literals::chrono_literals`
* `std::literals::complex_literals`
* `std::literals::string_literals`
* `std::literals::string_view_literals`
* `std::numbers` (mathematical constants)
* `std::pmr` (polymorphic memory resources)

If we want to use a *suffix* from a namespace, we have to introduce it into the namespace in which we want to use it. For example:

```cpp
using namespace literals::complex_literals; // make the complex literals visible
auto z = 2 + 3i;
```

Suffixes can not be explicitly qualified.

### The `ranges` namespace

> "To protect against ambiguities when using traditional unconstrained templates, the standard requires that we explicitly introduce the range version of a standard-library algorithm into a scope"

**What he means:** there are *two* `sort`s in the standard library:
* `std::sort(begin, end)` -- the classic, **unconstrained** template taking two iterators.
* `std::ranges::sort(range)` -- the newer, **concept-constrained** version taking a whole range.

If unqualified `sort(v)` could pull in *both* at once, the compiler could hit ambiguities (the old template is unconstrained, so it doesn't cleanly lose to the ranges one). To avoid that, `using namespace std;` deliberately does **not** make `std::ranges::sort` available as a bare `sort`. If you want the range version's short name, you must **explicitly** opt in -- either qualify it (`ranges::sort(v)`) or bring it in with a using-declaration (`using ranges::sort;`).

```cpp
using namespace std;

void g(vector<int>& v) {
    sort(v.begin(), v.end());   // OK
    sort(v);                    // error: no match function (in std)
    ranges::sort(v);            // OK
    using ranges::sort;         // sort(v) OK from here on
    sort(v);                    // OK
}
```

**Line by line (recall `using namespace std;` makes `std::` names -- including the sub-namespace `ranges` -- reachable):**
1. `sort(v.begin(), v.end())` -- ✅ finds `std::sort` (the two-iterator version). Standard usage.
2. `sort(v)` -- ❌ **error.** Unqualified `sort` only finds `std::sort`, which needs *two* iterators, not a single range. And `std::ranges::sort` is **not** visible as a bare `sort` (that's the whole point above), so nothing matches.
3. `ranges::sort(v)` -- ✅ explicitly qualified. `ranges` resolves to `std::ranges`, so this is `std::ranges::sort`, which *does* take a single range.
4. `using ranges::sort;` -- this is a **using-declaration** (`using std::ranges::sort;`). It pulls that one name into the local scope so `sort` now *also* refers to `ranges::sort`.
5. `sort(v)` -- ✅ **now OK.** After the using-declaration, unqualified `sort(v)` finds `ranges::sort`.

So the example is demonstrating the rule from the quote: the range algorithm's short name doesn't come for free -- you either qualify it (line 3) or explicitly introduce it (line 4) before the bare `sort(v)` works (line 5).

### Modules

The book was written pre-C++23. C++23 standardized `import std;` (and `import std.compat;`), which imports the whole standard library as a single named module. Much faster to compile than `#include`-ing many headers.

### Headers

> "Headers from the C standard library, such as `<stdlib.h>` are provided. For each such header there is also a version with its name prefixed by `c` and the `.h` removed. This version, such as `<cstdlib>` places its declarations in both the std and global namespace."

# A Tour of C++ (Stroustrup) — Ch. 10: Strings and Regex

---

C++ offers `string` for most standard string manipulation. The `string_view` type allows manipulating a sequence of characters however they may be stored (whether `std::string` or `char[]`). Then there's also `regex` for regular expression matching.

## Strings

The `string` class allows a variety of operations, including concatenation:

```cpp

const string name = "dmr";
const string domain = "bell-labs.com";
auto addr = name + '@' + domain;
```

Note that string concatenation can include `string`, a string literal, a C-style string, or a character.

A `string` is mutable. i.e. you can change a `std::string`'s contents **in place**, without creating a new object. That's unlike Java/C#/Python strings, which are *immutable* -- there, every "edit" allocates a brand-new string.

In addition to `=` and `+=`, subscripting (using `[]`) and substring operations are supported. The subscript operator is the key: `s[i]` returns a `char&` (a *reference*), so you can assign through it:

```cpp
string s = "cat";
s[0] = 'C';   // mutates in place → "Cat"; no new string allocated
```

`=`, `+=`, and `replace()` likewise modify the existing object. (Caveat: `substr()` is the odd one out -- it *returns a copy* and doesn't mutate the original. Stroustrup just lists it alongside the others as a supported operation.)

String also supports `replace`:

```cpp
string name = "Niels Stroustrup";
void m3() {
    string s = name.substr(6,10); // s = "Stroustrup"
    name.replace(0,5,"nicholas"); // name becomes "nicholas Stroustrup"
    name[0] = toupper(name[0]); // name becomes "Nicholas Stroustrup"
} 
```

You can create string literals of type `std::string` or `const char*`:

```cpp
auto cat = "Cat"s; // a std::string
auto dog = "Dog"; // a C-style string: a const char* 
```

### `string` implementation

As discussed in the CppCon Back To Basics talks, a `string` value can either be a "short string" or a "long string". The definition of "short" vs. "long" is compiler-specific.

## String Views

A `string_view` is a `(pointer, length)` pair denoting a sequence of characters. It is **not** null-terminated. It gives access to a contiguous sequence of characters.

This restriction means that we cannot have a `string_view` return value for a locally-allocated block of memory. This will fail:

```cpp
string_view bad() {
    string s = "Once upon a time";
    return {&s[5],4}; // bad: returning a pointer to a local
}
```

The local `string s` is destroyed when `bad()` returns, so the returned `string_view` **dangles** -- it points at freed characters. (Same non-owning/lifetime footgun as the strings CppCon talk.)

Also, string_view is only a **read-only** view of the characters. You cannot use a `string_view` to pass characters to a function that modifies its argument to lowercase. Instead, you'd need to use `span`.

## Regular Expressions

Regular expression support is provided by `#include <regex>` and the `std::regex` **type/class**. The regex facilities all live directly in namespace `std`: `std::regex`, `std::regex_match`, `std::smatch`, etc. With regex, we'll regularly want to use raw string literals like:

```cpp
regex pat {R"(\w{2}\s*\d{5}(-\d{4})?)"};
regex pat {"\\w{2}\\s*\\d{5}(-\\d{4})?"};
```

Note that these are the same, but we need the double backslashes on the second one, since it's not a raw string literal.

The `<regex>` standard library provides the following useful support functions:

* `regex_match()`: Match a regular expression against a string
* `regex_search()`: Search for a string that matches a regular expression in a stream of data
* `regex_replace()`: Search for a string that matches a regular expression in a stream of data and replace them
* `regex_iterator`: Iterate over matches and submatches
* `regex_token_iterator`: Iterate over *selected submatches* of each match, and -- when configured with the special index `-1` -- yields the text **between** matches. That `-1` mode is how you do **splitting/tokenizing** (e.g. split a CSV line on commas), which gives a way to iterate over "non-matches" as well.

> "The regular expression syntax and semantics are designed so that regular expressions can be compiled into state machines for efficient execution [Cox,2007]. The regex type performs this compilation at run time. "

**What this means:** a regex pattern (a string like `\d{5}`) gets turned into a **state machine** (a finite automaton) that can scan text efficiently. The key phrase is "**at run time**": that translation happens when your program *runs* -- specifically when the `std::regex` object is **constructed** -- not when your program is compiled.

Two practical consequences:
1. **Constructing a `regex` isn't free.** Build it **once** and reuse it; don't reconstruct the same pattern inside a loop.
2. **A bad pattern is caught at run time, not compile time.** An invalid regex throws `std::regex_error` when the object is built -- the C++ compiler never checks your pattern for you (it's just a string as far as it's concerned).

### Regex iterators

We can also use an iterator of the matches:

```cpp
void test() {
    string input = "aa as; asd ++e^asdf asdfg";
    regex pat {R"(\s+(\w+))"};
    for (sregex_iterator p(input.begin(),input.end(),pat); p!=sregex_iterator{}; ++p)
        cout << (*p)[1] << '\n';
} 
```

This would output:
```
as
asd
asdfg
```

> "A regex_iterator is a bidirectional iterator, so we cannot directly iterate over an istream (which  offers only an input iterator). Also, we cannot write through a regex_iterator, and the default  regex_iterator (regex_iterator{}) is the only possible end-of-sequence. "

**Three points here, all about iterator categories.** Iterators come in strength tiers -- weakest to strongest: *input → forward → bidirectional → random-access*. A weaker source can't satisfy a stronger requirement.

1. **"bidirectional, so can't iterate an istream directly."** Regex matching needs to re-scan characters (backtracking = multi-pass), so `regex_iterator` requires the underlying sequence to support at least a **bidirectional** iterator. An `istream` only offers an **input iterator** -- single-pass, read-once, can't go back. Input is *weaker* than bidirectional, so you can't run a regex_iterator straight over a stream. **Workaround:** read the stream into a `std::string` first, then regex over that.

2. **"cannot write through it."** It's **read-only** -- dereferencing gives you a `const match_results` (the match), so you can't modify the source through the iterator.

3. **"default `regex_iterator{}` is the only end-of-sequence."** The **sentinel** you compare against is always the default-constructed iterator. That's exactly the `sregex_iterator{}` in the loop above (`p != sregex_iterator{}`) -- there's no `.end()` to call; the empty iterator *is* the end marker.
