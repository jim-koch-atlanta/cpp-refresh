## Standard-Library Components

The STL contains a variety of components. The main criteria for including a class in the library were that:
* It could be helpful to almost every C++ programmer.
* It could be provided in a general form that did not add significant overhead compared to a simpler version of the same facility.
* Simple uses should be easy to learn.

## Standard-Library Organization

### Namespaces

The standard library is defined in the `std` namespace. People will usually use it with:

```cpp
#include <string>
using namespace std;
```

There are plenty of sub-namespaces:
* `std::chrono`
* `std::literals::chrono_literals`
* `std::literals::complex_literals`
* `std::literals::string_literals`
* `std::literals::string_view_literals`
* `std::numbers` (mathematical constants)
* `std::pmr` (polymorphic memory resources)

If we want to use a *suffix* from a namespace, we have to introduce it into the namespace in which we want to use it. For example:

```cpp
using namespace literals::complex_literals; // make the complex literals visible
auto z = 2 + 3i;
```

Suffixes can not be explicitly qualified.

### The `ranges` namespace

> "To protect against ambiguities when using traditional unconstrained templates, the standard requires that we explicitly introduce the range version of a standard-library algorithm into a scope"

**What he means:** there are *two* `sort`s in the standard library:
* `std::sort(begin, end)` -- the classic, **unconstrained** template taking two iterators.
* `std::ranges::sort(range)` -- the newer, **concept-constrained** version taking a whole range.

If unqualified `sort(v)` could pull in *both* at once, the compiler could hit ambiguities (the old template is unconstrained, so it doesn't cleanly lose to the ranges one). To avoid that, `using namespace std;` deliberately does **not** make `std::ranges::sort` available as a bare `sort`. If you want the range version's short name, you must **explicitly** opt in -- either qualify it (`ranges::sort(v)`) or bring it in with a using-declaration (`using ranges::sort;`).

```cpp
using namespace std;

void g(vector<int>& v) {
    sort(v.begin(), v.end());   // OK
    sort(v);                    // error: no match function (in std)
    ranges::sort(v);            // OK
    using ranges::sort;         // sort(v) OK from here on
    sort(v);                    // OK
}
```

**Line by line (recall `using namespace std;` makes `std::` names -- including the sub-namespace `ranges` -- reachable):**
1. `sort(v.begin(), v.end())` -- ✅ finds `std::sort` (the two-iterator version). Standard usage.
2. `sort(v)` -- ❌ **error.** Unqualified `sort` only finds `std::sort`, which needs *two* iterators, not a single range. And `std::ranges::sort` is **not** visible as a bare `sort` (that's the whole point above), so nothing matches.
3. `ranges::sort(v)` -- ✅ explicitly qualified. `ranges` resolves to `std::ranges`, so this is `std::ranges::sort`, which *does* take a single range.
4. `using ranges::sort;` -- this is a **using-declaration** (`using std::ranges::sort;`). It pulls that one name into the local scope so `sort` now *also* refers to `ranges::sort`.
5. `sort(v)` -- ✅ **now OK.** After the using-declaration, unqualified `sort(v)` finds `ranges::sort`.

So the example is demonstrating the rule from the quote: the range algorithm's short name doesn't come for free -- you either qualify it (line 3) or explicitly introduce it (line 4) before the bare `sort(v)` works (line 5).

### Modules

The book was written pre-C++23. C++23 standardized `import std;` (and `import std.compat;`), which imports the whole standard library as a single named module. Much faster to compile than `#include`-ing many headers.

### Headers

> "Headers from the C standard library, such as `<stdlib.h>` are provided. For each such header there is also a version with its name prefixed by `c` and the `.h` removed. This version, such as `<cstdlib>` places its declarations in both the std and global namespace."
