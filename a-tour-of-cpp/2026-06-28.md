## Concrete Types

> "The defining characteristic of a concrete type is that its representation is part of its definition."

**What he means**: a concrete type declares its **data members right in the class definition** (in the header). Because the compiler can see exactly what's inside, it knows the object's size -- so we can put it on the stack, copy it, and embed it as a member of another class, just like a built-in type. Trade-off: if I change the private data members, every file that uses the class must be **recompiled** (its size/layout changed).

(**Contrast**: an **abstract type** hides its representation -- the definition holds only the interface, and the real data lives in a hidden derived class. Changing it doesn't force users to recompile.)

Then later:

> "The class definition itself contains only the operations requiring access to the representation."

**What this means:** only put member functions that genuinely need to touch the private data *inside* the class. Anything that can be built from the public interface should be a **non-member (free) function**. Classic example: `complex::operator+=` needs the representation → member; binary `operator+` can be written using `+=` → free function. Minimizing the functions that touch the representation keeps the class small and easy to change.

> "User-defined operators ("overloaded operators") should be used cautiously and conventionally."

### Containers

Containers are a useful way to encapsulate and abstract away memory allocations. The `new` and `delete` calls will be contained within the implementation of the container.

One useful way to do initialization of a container is with an **initializer-list constructor**. For example:

```cpp
class Vector {
public:
  Vector();
  Vector(std::initializer_list<double>);
  ...
};
```

This could be defined:

```cpp
Vector::Vector(std::initializer_list<double> lst) // initialize with a list  
  :elem{new double[lst.size()]}, sz{static_cast<int>(lst.size())}
{
  copy(lst.begin(),lst.end(),elem); // copy from lst into elem
}
```

## Abstract Types

An *abstract type* is a type that insulates a user from implementation details. The interface is decoupled from the representation.

Here is an example of an abstract **container** class:

```cpp
class Container {
public:
  virtual double& operator[](int) = 0;  // pure virtual
  virtual int size() const = 0;         // const member function
  virtual ~Container() {}               // virtual destructor (essential for a base class)
};
```

Note that a **polymorphic type** is a class with virtual functions that provides an interface implemented by a variety of derived classes. (A type is "polymorphic" if it has at least one virtual function -- that's what enables runtime dispatch.)

When a derived class implements this interface, it can mark its functions `override` to state that they're overriding a base-class virtual. `override` has always been **optional**, but it makes the compiler verify that the function really does override a base virtual. So for that reason and for readability, it is a valuable keyword to use.

**How does the lookup of function implementations work?** Usually, the compiler will convert the name of a virtual function into an index into a table of pointers to functions. This is called the *virtual function table*, or vtbl. Each polymorphic object also carries a hidden pointer (the **vptr**) to its class's vtbl, so a virtual call is: follow the vptr → index into the vtbl → indirect-call the function found there.

Note that there is some overhead to the virtual call mechanism... it needs to do two extra memory loads (vptr, then the vtbl slot), plus an indirect branch. Also, it **cannot be inlined**, so we lose constant-propagation (usually the bigger cost).

## Class Hierarchies

> "A virtual destructor is essential for an abstract class because an object of a derived class is usually manipulated through the interface provided by its abstract base class."

This is important, since an object may be `delete`d via a pointer to its base class. So using a virtual call mechanism ensures that the proper destructor mechanism is called via the vtbl.

Note that class hierarchies tend to lead to use of **pointers** or **references** for a few reasons:

1. **Runtime dispatch** only works through a base **pointer or reference**, not a base *value*.
2. **Object slicing.** Copying a `Circle` into a `Shape` *by value* slices off the `Circle` part -- only the `Shape` subobject survives. Pointers/references avoid this.
3. **Runtime-determined type + ownership.** A factory that picks the concrete type at run time can't return a base *by value* (slicing again), so it returns e.g. `unique_ptr<Shape>` to a heap object. Same idea for heterogeneous collections like `vector<unique_ptr<Shape>>`.

## Advice

> "Use nonmember functions for symmetric operators;"

**Why:** a binary operator written as a **member** uses the left operand as the implicit `this`, and the left operand **won't undergo implicit conversion** to find the member -- only the right operand will. That breaks symmetry. Say `Complex` has a converting constructor from `double`:

```cpp
// member operator+:
c + 2.0;   // OK:    2.0 converts to Complex, then c.operator+(...)
2.0 + c;   // ERROR: 2.0 is a double; it has no operator+ member taking Complex
```

Make it a **non-member** and *both* operands convert equally, so both directions work:

```cpp
Complex operator+(Complex lhs, Complex rhs);  // free function
2.0 + c;   // OK now: 2.0 → Complex
```

So symmetric operators (`+`, `==`, `*`, ...) go outside the class -- as free functions (often `friend` if they need private access). Fits the earlier rule: only things needing the representation belong inside the class.

> "When designing a class hierarchy, distinguish between implementation inheritance and interface inheritance"

**Two different reasons to inherit:**

* **Interface inheritance** -- the base is a pure **abstract interface** (pure virtual functions, no data/code). Derived classes inherit the *contract* and supply their own implementations. Users depend only on the abstract base, so derived implementations can change freely. Loose coupling, clean polymorphism. (My `Container` above is this.)
* **Implementation inheritance** -- the base provides actual **data and/or function bodies** that derived classes **reuse** to avoid rewriting code. Convenient, but it **couples** derived classes to the base's internals -- changing the base can break them. More fragile.

Stroustrup's advice is to *know which one I'm doing*. Interface inheritance is usually the safer default; reach for implementation inheritance deliberately, aware of the coupling. Mixing them carelessly is how hierarchies turn brittle.
