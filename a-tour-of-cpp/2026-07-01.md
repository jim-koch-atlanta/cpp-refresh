## Concepts

We covered this with the CppCon Back To Basics talk on concepts. We want to be able to define algorithms / functions that are generic in a certain dimension. For example, we want algorithms that will operate upon *containers* or *types of elements*.

That requires the template arguments to meet specific requirements in order for the template to compile. For example, consider `sum()`:

```cpp
template<typename Sequence, typename Value>
Value sum(const Sequence& s, Value v)
{
    for (const auto& x: s)
        v+=x;
    return v;
} 
```

The type-name introducer `typename` requires only that the argument be a type. But what if the given type doesn't support ranges?

### Use of Concepts

Instead, we can specify **constraints** for the types:

```cpp
template<Sequence Seq, Number Num>
Num sum(const Seq& s, Num v)
{
    for (const auto& x: s)
      v+=x;
    return v;
} 
```

In this case, `Seq` must support the range interface (having a `begin()` and an `end()`), and Num must support `operator+`. We can do that:

```cpp
template<Sequence Seq, Number Num>
    requires Arithmetic<range_value_t<Seq>,Num>
Num sum(const Seq& s, Num n); 
```

The `range_value_t` of a sequence is the type of the elements in that sequence. Here we're saying that we should be able to do arithmetic operations between the elements in `Seq` and the type `Num`. So that'll work for mixed numerical types.

"Typically, when an algorithm requires arguments of differing types, there is a relationship between those types that it is good to make explicit." Unless the specification is complete, some errors won't be found until instantiation time.

The above `requires Arithmetic` is called a "requirements clause". Note that we can also write it these ways:

```cpp
template<typename Seq, typename Num>
  requires Sequence<Seq> && Number<Num> && Arithmetic<range_value_t<Seq>,Num>
Num sum(const Seq& s, Num n); 
```

```cpp
template<Sequence Seq, Arithmetic<range_value_t<Seq>> Num>
Num sum(const Seq& s, Num n); 
```

### Concept-based Overloading

It's possible that there could be more than one implementation of a templated function. For example:

```cpp
template<forward_iterator Iter>
void advance(Iter p, int n)// move p n elements forward
{
    while (n--)
        ++p;// a forward iterator has ++, but not + or +=
}

template<random_access_iterator Iter>
void advance(Iter p, int n)// move p n elements forward
{
    p+=n;// random access
}
```

If we used vector, it'll use the random_access_iterator implementation, since that's the strongest requirements.

> "For an alternative to be chosen it must be
>   • a match for all of its arguments, and
>   • at least an equally good match for all arguments as other alternatives, and
>   • a better match for at least one argument."

If there's not a best choice, the compiler will give an ambiguity error.

### Valid Code

Here's an example of a requires-expression. Note that the two `requires` are both needed, since the first starts the requires-clause:

```cpp
template<forward_iterator Iter>
    requires requires(Iter p, int i) {p[i]; p+i;}// Iter has subscripting and integer addition
void advance(Iter p, int n)// move p n elements forward
{
    p+=n;
} 
```

Note that this could still pass concept checking and fail to compile. The `requires(Iter p, int i){ p[i]; p+i; }` only checks that `p[i]` and `p+i` are **valid expressions** -- but the body uses `p += n`, which was **never required**. So a type with `[]` and `+` but no `+=` would *satisfy the concept* yet *fail to compile in the body*. Lesson: **a requires-expression only guarantees exactly what you list.** (Also, `{ p[i]; p+i; }` are *simple* requirements -- they don't constrain the **result types**; to do that you'd need compound requirements like `{ p+i } -> same_as<Iter>;`.)

Also note the doubled keyword: `requires requires`. The **first** `requires` starts the requires-*clause* (the constraint on the template); the **second** starts a requires-*expression* (the inline ad-hoc predicate). Same two-meanings-of-`requires` distinction from the concepts talk -- here they just sit adjacent.

### Definition of Concepts

> The result of an {...} specified after a -> must be a concept. Unfortunately, there isn’t a standard-library `boolean` concept, so I defined one. `Boolean` simply means a type that can be used as a condition.

**What that first sentence means -- compound requirements.** Inside a requires-expression there are three flavors of requirement. This section is about the third:

```cpp
requires (T a, T2 b) {
    a.size();                       // 1. simple requirement: "this expression must be valid"
    typename T::value_type;         // 2. type requirement: "this type must exist"
    { a == b } -> Boolean;          // 3. compound requirement: valid AND its result satisfies a concept
}
```

The `{ expr } -> Something` form checks two things: that `expr` compiles, **and** that the *type of its result* satisfies `Something`. The rule Stroustrup is stating: **whatever follows `->` must be a `concept`, not a plain type.** So this is illegal:

```cpp
{ a == b } -> bool;                  // ❌ ill-formed: bool is a type, not a concept
{ a == b } -> std::same_as<bool>;    // ✅ same_as<bool> is a concept
{ a == b } -> std::convertible_to<bool>;  // ✅ also a concept
```

**Where is capital `Boolean` defined? He defined it himself** -- it's *his own* concept, written earlier in the chapter, not from the standard library. That's the whole point of "there isn't a standard-library `boolean` concept, so I defined one." (`==` should yield something usable as a condition, i.e. convertible to `bool`; there's no ready-made std concept named exactly that, though `std::convertible_to<bool>` does the job. C++20 does have an *exposition-only* `boolean-testable`, but it's not a public name you can use.)

Spacing cleaned up:

```cpp
template<typename T, typename T2 = T>
concept Equality_comparable =
    requires (T a, T2 b) {
        { a == b } -> Boolean;   // compare a T to a T2 with ==
        { a != b } -> Boolean;   // compare a T to a T2 with !=
        { b == a } -> Boolean;   // compare a T2 to a T with ==
        { b != a } -> Boolean;   // compare a T2 to a T with !=
    };
```

The `T2 = T` default is neat: `Equality_comparable<X>` checks a type against *itself* (homogeneous), while `Equality_comparable<X, Y>` checks cross-type comparison.

He then defines concepts for Number, Arithmetic, and Sequence.

### Concepts and `auto`

You can use `auto` with concepts too. So like we can have sum defined like this:

```cpp
template<Number Num>
    requires Arithmetic<Num,Num>
Num sum(Num n1, Num n2) { return n1 + n2; }
```

**or** like this (**abbreviated function template** syntax):

```cpp
auto sum(Arithmetic auto n1, Arithmetic auto n2) { return n1 + n2; }
```

**Yes, that's valid syntax -- but the two are NOT equivalent (I verified this with g++).** The difference is subtle and important:

* `template<Number Num> Num sum(Num n1, Num n2)` -- **one** template parameter, so **both** args must be the *same* type. `sum(3, 4.5)` → **compile error** ("deduced conflicting types for Num: int and double").
* `auto sum(Arithmetic auto n1, Arithmetic auto n2)` -- each `auto` introduces its **own independent** invented template parameter, so the args can be **different** types. `sum(3, 4.5)` → **compiles fine**.

In other words, `Concept auto` is shorthand that desugars to:

```cpp
template<Arithmetic T1, Arithmetic T2>
auto sum(T1 n1, T2 n2) { return n1 + n2; }
```

**Why use `auto`?** Two reasons:
1. **Terser** -- no `template<...>` header, no naming types you don't otherwise refer to.
2. **Less constraining by default** -- each parameter is independently deduced, so you *don't* accidentally force two arguments to be identical types (which the named-`Num` version does). Use the named form only when you actually need to **name** the type (e.g. as the return type, or to require two params match). That's the "least constraining version" idea: reach for `auto` unless you need the name.

## Generic Programming

With algorithms and functions, we can genericize by using concepts. He gives a few examples of useful ones:

* `regular`
  * can be default constructed
  * can be copied using a constructor or assignment
  * can be compared using `==` and `!=`
* `totally_ordered`: Can be compared with `<`, `<=`, `>`, `>=`, `<=>`
* `forward_range`: Has `begin()` and `end()`

The process of generalizing from a concrete piece of code while preserving performance is called *lifting*.

## Variadic Templates

Defining variadic types is done by splitting head from tail, and recursing:

```cpp
template<typename T>
concept Printable = requires(T t) { std::cout << t; };

template<Printable T, Printable... Tail>
void print(T head, Tail... tail)
{
    cout << head << ' ';
    if constexpr(sizeof...(tail) > 0)
        print(tail...);
}
```

Key pieces:
* `Printable... Tail` -- a **template parameter pack** (zero or more types).
* `Tail... tail` -- a **function parameter pack**; `print(1, "hi", 2.0)` binds `head=1` and `tail=("hi", 2.0)`.
* `sizeof...(tail)` -- the **number of elements** in the pack (not a byte size!).
* `print(tail...)` -- **pack expansion**: re-calls `print` with the tail spread as separate arguments, peeling one off each time.
* The `if constexpr(sizeof...(tail) > 0)` guard means **no separate base-case overload is needed** -- when the pack is empty the recursive call is discarded at compile time. (The old pre-C++17 style needed a zero-arg `print()` overload to stop the recursion.)

You can also use **fold expressions**:

```cpp
template<Number... T>
int sum(T... v)
{
    return (v + ... + 0);
}
```

> "The first element to be added is the "rightmost" (the one with the highest index): (v[0]+(v[1]+(v[2]+(v[3]+(v[4]+0)))))"

That's a "right fold". You can also use a left fold with `return (0 + ... + v);`
