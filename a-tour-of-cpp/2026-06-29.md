# A Tour of C++ (Stroustrup) — Ch. 6: Essential Operations

---

## Essential Operations

Constructors, destructors, and copy and move operations must be defined as a matched set.

> "If you are explicit about some defaults, other default definitions will not be generated."

So if you define **one** of them, ensure that you define **all** of them. (This is the **Rule of Five**.)

Better yet, the **Rule of Zero**: if the class doesn't directly manage a raw resource, define **none** of the five and let the compiler generate them. Only hand-write them when managing a resource -- and even then, prefer wrapping the resource in a handle so you can get back to zero.

### Default, Delete

You can specify to use the default implementation with `=default`. You can specify that an operation should not be generated or allowed with `=delete`. As a good example, we wouldn't want to allow copy for a base (virtual) class.

### Conversions

A single-argument constructor that is **not** marked `explicit` defines an **implicit conversion** from the argument type to the class type. Marking it `explicit` **disables** that -- the object can then only be built explicitly (direct-initialization), not via `=`. For example:
```cpp
class Vector {
public:
    explicit Vector(int s);
    ...
};

...

Vector v1(7);   // OK: direct-initialization
Vector v2 = 7;  // error: copy-init needs an implicit int→Vector conversion, which `explicit` forbids
```

> "Use `explicit` for constructors that take a single argument unless there is a good reason not to."

## Copy and Move

By default, copy is a *memberwise* copy: copy each member of the class. This is probably fine for simple concrete types, but not for sophisticated concrete types or abstract types.

### Copying Containers

Keep in mind that if pointers are being used, we likely need to allocate new memory blocks for the new instance.

### Move Containers

If an object is particularly large, we will want to be able to move it for performance reasons. For example with Vector:

```cpp
Vector::Vector(Vector&& a)
  :elem{a.elem}, // "grab the elements" from a
  sz{a.sz}
{
    a.elem = nullptr; // now a has no elements
    a.sz = 0;
} 
```

We saw it with the CppCon talks -- the `&&` means rvalue reference. So the object is made available to the move constructor **without copying**, **and** it can be modified by this function.

(Worth marking move operations `noexcept` -- recall from the error-handling notes that `std::vector` only *moves* its elements on reallocation if the move is `noexcept`; otherwise it copies.)

## Resource Management

> "Resource handles, such as Vector and thread, are superior alternatives to direct use of built-in pointers in many cases. In fact, the standard-library ‘‘smart pointers,’’ such as unique_ptr, are themselves  resource handles"

**A "resource handle" is just an object that *owns* a resource and releases it in its destructor (RAII).** The resource can be anything: heap memory, a thread, a file, a lock, a socket. A smart pointer is *one kind* of resource handle -- the book's point is that the idea is **broader** than smart pointers:

* `Vector` owns a heap array (ctor allocates, dtor frees) -- a resource handle with a *container* interface.
* `std::thread` owns a thread of execution.
* `std::string`, `std::lock_guard`, `std::fstream` -- all resource handles.
* `std::unique_ptr` owns a heap object -- a resource handle with a *pointer* interface.

So instead of juggling raw pointers + manual `new`/`delete`, I wrap the resource in a handle whose scope-bound lifetime manages it. "Smart pointers are themselves resource handles" = they're just a special case of this one general RAII pattern.

## Conventional Operations

> "<=> implements a three-way-comparison. A negative return value means less than, 0 means equal, and a positive value means greater-than."

**Two refinements:**

1. `<=>` doesn't actually return an `int` -- it returns a **comparison category**: `std::strong_ordering`, `std::weak_ordering`, or `std::partial_ordering`. The negative/zero/positive intuition still works because those results compare against the literal `0` (e.g. `(a <=> b) < 0`).
2. The real superpower: **`= default` it and get all six comparisons for free.**

```cpp
struct Point {
    int x, y;
    auto operator<=>(const Point&) const = default;
};
```

A defaulted `<=>` lets the compiler rewrite `<`, `>`, `<=`, `>=` in terms of it, and it also implicitly defaults `==` (which gives `!=`). One line → all of `< > <= >= == !=`, compared memberwise/lexicographically. *That's* why `<=>` exists.

### `swap()`

`std::swap()` is implemented as three `move` operations. If a type is expensive to copy and could possibly be swapped, then give it a `move` or `swap()` function.

### `hash<>`

In order for a type `K` to be the key in a hash table `unordered_map<K,V>`, `hash<K>` must be defined.

## User-defined literal operators

You can specify that a literal is of a certain type by using a **user-defined literal operator**. For example, we could specify the *imaginary number 1* with `1i`. To define the `i` operator, it would be:

```cpp
constexpr complex<double> operator""i(long double arg) {
    return {0, arg};
}
```

> ⚠️ **Naming rule:** literal suffixes that **don't** start with an underscore (like `i` here) are **reserved for the standard library** -- in fact `i` *is* a std literal (`std::complex_literals`), which is why this example reuses it. My *own* UDLs must start with an underscore, e.g. `operator""_i`.

## Parameterized Types

I've seen and done this before...
```cpp
template<typename T>
class Vector {
private:
    T* elem;
    ...
};
```

It's like the mathematical "for all T". If we want the mathematical concept of "for all T, such that P(T)", we use concepts. Concepts let the compiler do type checking at the point of use, giving better error messages far earlier than is possible with unconstrained template arguments.

### Value Template Arguments

This is kinda cool... we can pass a value argument to a template like:

```cpp
template<typename T, int N>
struct Buffer {
    constexpr int size() { return N; }
    T elem[N];
    ...
};
```

Notice that we're able to define a sized **buffer** of N elements, which is not something we'd normally be able to do. (`N` is a compile-time constant, so `T elem[N]` is a fixed-size array member -- the same "array bounds need a constant expression" rule from Ch. 1.)

### Template Argument Deduction

He gives this example:

```cpp
template<typename T>
class Vector {
public:
  Vector(initializer_list<T>);// initializer-list constructor 
  
  template<typename Iter>
    Vector(Iter b, Iter e);// [b:e) iterator-pair constructor
    
    struct iterator {using value_type = T; /*... */}; 
    
    iterator begin();  //  ...
}; 
```

What would happen on:
```cpp
Vector v3(9, 17);
```

"Is that a pair of iterators, or a pair of values of type iterator?" (Huh?)

How do we specify, "A pair of values of the same type should be considered iterators"? We can use a *deduction guide*:

```cpp
template<typename Iter>
    Vector(Iter, Iter) -> Vector<typename Iter::value_type>;
```

That will result in:
```cpp
Vector v1 {1, 2, 3, 4, 5};// element type is int 
Vector v2(v1.begin(),v1.begin()+2);// pair-of-iterators: element type is int
Vector v3 {v1.begin(),v1.begin()+2};// braces → element type is Vector<int>::iterator (!)
```

**My guess is right.** This is **CTAD** (Class Template Argument Deduction, C++17): writing `Vector v1 {1,2,3}` instead of `Vector<int> v1 {...}` and letting the compiler deduce the element type from the constructor arguments.

The problem: the iterator-pair constructor `Vector(Iter b, Iter e)` never mentions `T`, so the compiler can't figure out the element type from it. The **deduction guide** supplies the missing link:

```cpp
template<typename Iter>
Vector(Iter, Iter) -> Vector<typename Iter::value_type>;
```

It reads exactly as I guessed: "if a `Vector` is built from two args of the same type `Iter`, the element type is `Iter::value_type`." So `Vector v2(v1.begin(), v1.begin()+2)` deduces to `Vector<int>` (an int-iterator's `value_type` is `int`).

**The gotcha (why the three results differ): braces vs parens.**
* `{...}` *prefers the `initializer_list` constructor*.
* `(...)` uses normal overload resolution.

```cpp
Vector v1 {1, 2, 3, 4, 5};             // initializer_list<int>          → Vector<int>
Vector v2(v1.begin(), v1.begin()+2);   // parens → iterator-pair + guide → Vector<int>
Vector v3 {v1.begin(), v1.begin()+2};  // braces → initializer_list of iterators → Vector<Vector<int>::iterator>!
```

So `v3` with braces is a vector **of iterators** -- same arguments as `v2`, different deduced type, purely because of `{}` vs `()`.

And `Vector v3(9, 17)` (the puzzle on the "Huh?" line): `9` and `17` are `int`s, and `int` has no `::value_type`, so the guide doesn't apply and deduction fails. That's the *intended* safety -- two ints aren't iterators, so the compiler refuses rather than silently treating them as a begin/end pair.

## Parameterized operations

There are a few different types of parameters operations

### Function templates

You can specify that the parameters to a function are templated much like a class:

```cpp
template<typename Sequence, typename Value>
Value sum(const Sequence& s, Value v) {
    ...
}
```

### Function objects

This one was new and interesting. You can define an object that's also a function. For example:

```cpp
template<typename T>
class Less_than {
    const T val;
public:
    Less_than(const T& v) : val{v} { }
    bool operator()(const T& x) const { return x < val; }
};
```

So that's a good way to pass a value around alongside a defined operation -- a function object carries **state** (here `val`) *and* behavior, and a lambda is really just shorthand for one of these.

### Lambda expressions

They will be of the form:
```cpp
[&](P p){ return ...; }
```

**Note**: `[&]` is a *capture list*. It means that all local variables are available to the lambda, passed by reference. `[=]` means all local variables are available to the lambda, passed by *value*. `[x]` means that just the local variable `x` is available to the lambda. And `[*this]` means to make a copy of the current object available to the lambda. (Contrast `[this]`, which captures the *pointer* -- members are then accessed by reference on the original object; `[*this]` copies the whole object, which is safer if the lambda outlives `this`.)

## Compile-time `if`

They give this example as something that does **not** work:
```cpp
template<typename T>
void bad(T arg) {
    if constexpr (!is_trivially_copyable_v<T>)
        try {           // Oops: this 'if' controls only the 'try', and now the
            g(arg);      // try/catch is split across two separate statements

    if constexpr (!is_trivially_copyable_v<T>)
        } catch(...) { /* ... */ }   // syntax error
}
```

**Why it fails:** `if constexpr` is **not** the preprocessor. It discards the not-taken branch, but only *after* the code is parsed, and it selects a **complete statement**. The broken code tries to use two separate `if constexpr`s to emit a lone `try {` and, later, a lone `} catch(...) {...}`. Neither piece is a complete statement -- a `try` with no `catch`, and a `} catch` with no `try`, can't be parsed at all. So it's a syntax error *before* any branch is even discarded.

The fix: put the **whole** try/catch inside one branch.

```cpp
template<typename T>
void ok(T arg) {
    if constexpr (!is_trivially_copyable_v<T>) {
        try { g(arg); }
        catch (...) { /* ... */ }
    } else {
        g(arg);
    }
}
```

Mental model: `if constexpr` chooses *which complete statement to keep*; everything must still be syntactically valid C++ either way. `#ifdef` cuts text; `if constexpr` does not.
