## Constant expressions

A **constant expression** is one the **compiler can evaluate at compile time** — its
value is fixed and known *before the program runs*. The opposite is a value only
knowable at runtime (read from input, returned by a normal function call, computed
from user data).

A few places **require** a constant expression, because the compiler needs the value
*while compiling*, not later:

| Context | Why a constant is required |
|---|---|
| **Array bounds** `int a[N];` | Compiler must reserve exactly that much memory as it compiles |
| **`case` labels** | A `switch` compiles to a jump table; each label must be a fixed value |
| **Template value args** `std::array<int, 5>` | Templates are instantiated at compile time |
| **`constexpr` constants** | By definition — the initializer must be a constant expression |

```cpp
constexpr int n = 10;
int a[n];                 // ✅ n is a constant expression
std::array<int, n> arr;   // ✅
switch (x) { case n: ...} // ✅

int m = read_int();       // runtime value
int b[m];                 // ❌ size not known at compile time (not standard C++)
```

### `const` ≠ constant expression

A `const` variable is usable in those contexts **only if its initializer was itself a
constant expression**:

```cpp
const int a = 10;          // constant expression  → usable as an array bound
const int b = read_int();  // const, but a RUNTIME value → NOT a constant expression
int arr1[a];   // ✅
int arr2[b];   // ❌
```

- `constexpr` makes the guarantee **explicit and compiler-enforced**: "this *is* a
  constant expression."
- A plain `const` only *happens* to be one if you got lucky with the initializer.

> **Unifying idea:** all four contexts are resolved by the compiler before runtime, so
> all four demand a value the compiler can compute at compile time.

## Argument passing & return are *initialization*

> "The basic semantics of argument passing and function value return are that of
> initialization."

**Each parameter is a new variable initialized from its argument.** The return
slot (or the variable receiving the result) is initialized from the return
expression. So you can mentally rewrite a call as a declaration:

```cpp
void f(int x);

int a = 5;
f(a);     // semantically:  int x = a;   ← x is initialized from a
```

There is **no separate "argument passing" rule set** — whatever the rules of
*initialization* are, those are the rules of passing and returning. One concept,
reused.

### Pass-by-reference falls out for free

Make the parameter a **reference** and apply the same "it's just initialization" rule:

```cpp
void byValue(int x);           //  int x = a;        → COPY of a        → pass-by-value
void byRef(int& x);            //  int& x = a;       → BINDS to a       → pass-by-reference
void byConstRef(const int& x); //  const int& x = a; → binds, read-only → pass-by-const-ref
```

Pass-by-reference isn't a special mechanism — it's just what initializing a
**reference** already does: bind the new name to the caller's existing object instead
of copying it.

### Return works the same way

```cpp
int  make() { int t = 42; return t; }                 // result initialized from t (copy/move)
int& at(std::vector<int>& v, int i) { return v[i]; }  // result is a reference bound to v[i] — no copy
```

### Tie-back to move semantics (2026-06-24 notes)

Initialization is exactly where the compiler decides **copy vs. move**, so move
semantics work *through* function calls:

- lvalue → by-value parameter → **copy** constructor
- rvalue / `std::move(x)` → by-value parameter → **move** constructor
- `const T&` parameter accepts a temporary → legal reference binding
  (same rule as `const double& rd = 1;`)
- `T&&` parameter binds only to rvalues → reference-binding rules during passing

> **One-line takeaway:** *parameter = a variable initialized from the argument;
> return value = a variable initialized from the return expression.* Learn
> initialization once, and calls and returns come along for free.
