## `import`

To define a module, we use `export` --
```cpp
export module Vector;

export class Vector {
public:
    Vector(int s);
    double & operator[](int i);
    int size();
...
}
```

Then it is imported with:
```cpp
import Vector;

double sqrt(Vector& v) {
  ...
}
```

You can have both `import` and `#include` in files, so this allows for gradual migration. There are a few key differences between modules and headers:
* A module is compiled only once. Headers are compiled in each translation unit that includes them.
* Two modules can be imported in either order without changing their meaning.
* `import` is not transitive. If you `import` a module, and that module `import`s something, you have not implicitly gained access to that something.

So this tends to make compilation dramatically faster with modules than with `#include`'ing headers.

## Namespaces

I knew all of this... be cautious with `using namespace X;` (a using-*directive*) -- it dumps **all** of the namespace's names into scope at once, so you risk clashes. When I only want a few names, prefer using-*declarations* like `using std::string;` to stay selective.

## Function Arguments and Return Values

This is covering what I saw yesterday in the CppCon talk on [static, inline, const, & constexpr](../cppcon/2026-06-25-static-inline-const.md).

### Value Return

When talking about returning a very large object, it gives the example of a "Matrix":

> We should *not* regress to use manual memory management:
>
> ```cpp
> Matrix* add(const Matrix& x, const Matrix& y) {
>     Matrix* p = new Matrix;
>     ...
> }
> ```

What *should* be used: just **return the `Matrix` by value**. `Matrix` manages its own memory (RAII), so returning it is cheap -- the compiler uses **copy elision / NRVO** to build the result directly in the caller, with zero copies. And even when NRVO doesn't apply, a returned local is treated as an rvalue, so I get an **implicit move** for free.

**Note**: This is *not* a good place for `std::move()` on the return. `return std::move(res);` actually **suppresses NRVO** -- the result is no longer a plain name the compiler can elide, so it forces a move where elision would've cost *nothing*. Plain `return res;` is best: let NRVO win, and fall back to the implicit move automatically.

### Suffix (Trailing) Return Type

I assumed this was mainly a lambda thing -- and for **lambdas it's the only way** to state the return type explicitly (you can't write `double [](int x){}`).

However, it **can** also be used for named functions:

```cpp
auto mult(double d1, double d2) -> double { return d1 * d2; }
```

For a trivial case like `mult`, the trailing form buys nothing -- I'd just write `double mult(...)`. It's worthwhile for for named functions when we **can't name the return type up front**:

```cpp
template <typename T, typename U>
auto add(T t, U u) -> decltype(t + u) { return t + u; }   // return type depends on the args
```

Other real uses: class-scope name lookup when defining a member out-of-class (`auto Widget::items() -> Iterator` finds `Iterator` inside `Widget`), SFINAE via `-> decltype(expr)`, and just left-aligning names as a style choice.

**Why can't I just prefix the return type as `decltype(t + u)`?** Two reasons:
1. `T + U` isn't a thing -- `+` works on **values**, not types. `decltype` needs an expression, so it uses the parameter variables `t`/`u`.
2. **Scope/ordering.** Name lookup is left-to-right; in the leading position the return type comes *before* the parameter list, so `t` and `u` aren't declared yet. The trailing form exists to move the return type *after* the params, where their names are finally visible. The leading `auto` is just a placeholder for "real type comes after `->`".

```cpp
decltype(t + u) add(T t, U u);          // ❌ t, u not in scope yet
auto add(T t, U u) -> decltype(t + u);  // ✅
```

I *can* force a leading return type with `std::declval` (uses only the type names, which are in scope), but it's ugly: `decltype(std::declval<T>() + std::declval<U>()) add(T t, U u)`. And in C++14+ I can skip all of it -- `auto add(T t, U u) { return t + u; }` deduces it.
