## Exceptions

The main way that errors are handled in C++ is via **exceptions**. When an error situation occurs, an exception is thrown:

```cpp
double& Vector::operator[](int i) {
  if (!(0<=i && i<size()))
    throw out_of_range{"Vector::operator[]"};
  return elem[i];
} 
```

Somewhere up the call stack at an appropriate location, the exception can be caught and handled:

```cpp
try {
  // out_of_range exceptions thrown in this block are handled by the handler defined below
  compute1(v);// might try to access beyond the end of v
  Vector v2 = compute2(v);// might try to access beyond the end of v
  compute3(v2);// might try to access beyond the end of v2
}
catch (const out_of_range& err) {// oops: out_of_range error
  //... handle range error...
  cerr << err.what() << '\n';
} 
```

Notice the use of the `what()` function to get additional error context.

**Why RAII comes up here (I get it now):** when an exception is thrown, the stack *unwinds* -- as control jumps from the `throw` up to the matching `catch`, every local object in the abandoned frames has its **destructor called automatically**. RAII means resources (memory, files, locks) are owned by objects, so those destructors release them. That's what makes exceptions safe: I can bail out of the middle of a computation and nothing leaks.

It's **not** about the `operator[]` access itself -- it's about everything *between* the throw and the catch. In the `try` block above, if `compute3(v2)` throws, the local `Vector v2` still gets destroyed during unwinding (its `elem[]` buffer is freed -- no leak), even though I never reached the end of the block. Without RAII (manual `new`/`delete`, manual file close) the throw would skip the cleanup and leak.

This is also why Stroustrup says try-blocks should be rare: don't catch just to clean up by hand -- let destructors do it.

## Error-Handling Alternatives

* **When to return an error code**:
  * Failure is normal. For example, failure to open a file.
  * The immediate caller can handle the failure.
  * An error happens in a set of parallel tasks, and we care which specific task failed.
  * The system is low on memory, and run-time error support for exceptions would take up too much more.
* **When to throw an exception**:
  * When errors are extremely rare.
  * The error needs to be handled by an "ultimate caller" higher up the call stack.
  * New kinds of errors can be added in lower-level modules without rewriting the layers above. (*This confused me -- here's the point:* with exceptions, a deep function can throw a brand-new exception type and it propagates straight up to wherever it's caught; the intermediate functions don't need to know about it or pass it along. With **error codes** it's the opposite -- every function in the chain has to be edited to check for the new code and forward it up. Stroustrup's example: making a single-threaded app multi-threaded, or moving a resource onto the network, introduces new low-level failures; exceptions let me add the `throw` down low and the `catch` up high, leaving the middle untouched.)
  * There's no way to return an error code. For example, a constructor.
  * Returning both a value *and* an error status would make the return path messy or expensive (forcing a `pair`, out-parameters, or a separate error flag).
  * Recovery from an error depends on the results of multiple function calls, so it would be difficult to do as errors.
  * Callbacks.
  * An error implies that an "undo action" is needed -- exceptions shine here because stack unwinding + RAII *performs* the undo automatically (destructors roll back what was acquired). (My "but there may not be an undo action" was backwards -- the point is the opposite: when undo *is* needed, exceptions handle it cleanly.)
* **When to terminate**:
  * It's not possible to recover from the error.
  * The system is designed to just restart a thread or process for errors.

## Assertions

He builds a little `expect()` helper to show how to pick an error-handling strategy:

```cpp
enum class Error_action { ignore, throwing, terminating, logging };
constexpr Error_action default_Error_action = Error_action::throwing;

template <Error_action action = default_Error_action, class C>
constexpr void expect(C cond, std::string_view mess) {
    if constexpr (action == Error_action::throwing)
        if (!cond()) throw Assert_error{mess};
    if constexpr (action == Error_action::terminating)
        if (!cond()) std::terminate();
    // ... logging / ignore ...
}
```

**How is it set?** -- it's a *compile-time* setting, so effectively hard-coded.** `default_Error_action` is a `constexpr` constant that can be edited, and the strategy is selected with `if constexpr` (the branches not taken are *discarded* -- zero runtime cost; the same `if constexpr` from the [static/inline/const talk](../cppcon/2026-06-25-static-inline-const.md)). To override per call, I pass an explicit template arg: `expect<Error_action::terminating>(...)`. There's no runtime switch -- that's the whole point: the unused error-handling code isn't even compiled.

### `assert()` (runtime)

The standard `assert(cond)` macro (`<cassert>`) checks a condition **at run time**; if it fails, the program aborts. It's **disabled when `NDEBUG` is defined** (release builds), so never put side effects inside an `assert()` -- they'll vanish in release.

### `static_assert()` (compile time)

`static_assert(cond, "message")` checks a **constant expression at compile time** and fails the build with the message if false:

```cpp
static_assert(sizeof(int) >= 4, "ints are too small");
```

Only works on things known at compile time (constant expressions, `sizeof`, type traits, concepts) -- ties back to the "constant expressions" notes from Ch. 1.

### `noexcept`

A function that should never throw an exception can be declared `noexcept`. If it still throws, `std::terminate()` is called immediately to terminate the program.

Bonus tie-back to the move-semantics talk: marking move operations `noexcept` matters for *performance* -- e.g. `std::vector` will only **move** its elements during reallocation (instead of copying) if their move constructor is `noexcept`. If it might throw, the vector copies instead, to preserve the strong exception guarantee.
