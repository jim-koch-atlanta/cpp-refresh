## Tasks and `thread`s

**Task**: A computation that can potentially be executed concurrently with other computations.

**Thread**: A system-level representation of a task in a program.

A task is a function or a function object:

```cpp
void f();                 // function

struct F {                // function object
    void operator()();    // F's call operator (§7.3.2)
};

void user() {
    thread t1 {f};        // f() executes in a separate thread
    thread t2 {F{}};      // F{}() executes in a separate thread
    t1.join();            // wait for t1
    t2.join();            // wait for t2
}
```

The `join()` calls ensure that we don't exit `user()` until both threads complete. To "join" a thread means to wait for it to terminate.

It's easy to forget to `join`, so the standard library provides `jthread`, which is a "joining thread" that follows RAII by having its destructor call `join()`.

**Note to self:** that's only *half* of `jthread`. It also carries a **`stop_token`**, and its destructor calls **`request_stop()` before it joins**. So `jthread` = auto-join **+** cooperative cancellation built in. (See "Stopping a thread" below — this is the whole `jthread` vs. my manual `thread`+`join` story.)

Threads share an address space, so they can communicate through shared objects.

Keep in mind that even `cout` shouldn't be leaned on inside threads. While it won't **crash** under concurrent writes (no data race on the stream object), it may **interleave** the output — tokens from different threads get jumbled. So we'd introduce locking ourselves, or use `osyncstream`, which buffers a thread's output and flushes it contiguously. **Note to self:** the risk is *jumbled* output, not corruption.

### Passing Arguments

We can pass arguments as well:

```cpp
void f(vector<double>& v);

int main() {
    vector<double> vec1 { 1, 2, 3, 4, 5 };
    jthread t1 {f, ref(vec1)};
}
```

> The initialization with `{f, ref(some_vec)}` uses a `thread` variadic template constructor that can accept an arbitrary sequence of arguments (§8.4). The `ref()` is a type function from `<functional>` that unfortunately is needed to tell the variadic template to treat `some_vec` as a reference, rather than as an object.

**Note to self:** thread args are **copied** (decay-copied) unless I say `ref()`. Forgetting `ref()` means the thread works on a copy — or a compile error for non-const refs, since you can't bind a `T&` to the thread's internal temporary. This is the same "am I sharing or copying?" question from the goose writer — anything I hand a thread by reference needs `ref()`, or I capture-by-reference in a lambda instead.

### Returning Results

Typically, results of threads will be passed in one of two ways:

1. As a non-const reference, like above.
2. As a separate result argument.

**Note to self:** these are the *crude* ways — I allocate the result slot, I synchronize it, and **an exception in the thread can't get home** (an uncaught exception in a raw thread function calls `std::terminate`). The `future`/`promise`/`async` machinery in "Communicating Tasks" is the modern fix — it hands the result back *and* carries exceptions across the thread boundary.

## Sharing Data

There are several approaches to ensuring multiple tasks can access the same data.

### `mutex`es and Locks

A `mutex` (mutual exclusion object) is a way to ensure that only one thread can operate upon shared state:

```cpp
mutex m;    // mutex
int sh;     // shared data
// ...
{
    scoped_lock lck {m};
    sh += 7;
}
```

The `scoped_lock`'s constructor acquires the mutex by calling `m.lock()`. If another thread already has the mutex, this thread waits ("blocks") until the other completes its access.

RAII resource handles like `scoped_lock` and `unique_lock` are much easier (and safer) than explicitly locking and unlocking a mutex.

Note that `scoped_lock` allows acquiring multiple locks simultaneously — and it does so **deadlock-free** (it uses a lock-ordering algorithm so two threads grabbing the same set can't deadlock):

```cpp
scoped_lock lck {mutex1, mutex2, mutex3};
```

**Note to self — the lock decision rule:**
- **`lock_guard`** — simplest RAII lock: **one** mutex, can't move, no manual unlock. The legacy single-mutex tool.
- **`scoped_lock`** — like `lock_guard` but **variadic** (one *or many* mutexes, deadlock-free). **My default** for "just guard this scope."
- **`unique_lock`** — the **flexible** one: **movable**, supports **deferred**/**timed** locking, and manual **`lock()`/`unlock()`**. Costs a bit more (tracks ownership state).
- **Rule:** reach for `scoped_lock` by default; upgrade to `unique_lock` **only** when you need its flexibility — a condvar `wait` (which must unlock + relock), moving the lock around, or manual/deferred/timed locking.

The most common way to share data is between multiple readers and a single writer. This "reader-writer lock" idiom is supported by `shared_mutex`:

```cpp
shared_mutex mx;

void reader() {
    shared_lock lck {mx};    // shared (read) ownership -- many readers at once
    // ...
}

void writer() {
    unique_lock lck {mx};    // exclusive (write) ownership -- one writer, no readers
    // ...
}
```

### `atomic`s

The `atomic` saves us from most uses of a more expensive `mutex`.

`atomic` does **not** bake in a mutex. For example, `atomic<int>` is **lock-free** — it compiles to hardware atomic instructions (verified: `atomic<int>::is_always_lock_free == 1`). Only *oversized* atomics fall back to an internal lock (verified: a 64-byte `atomic<Big>` reports `is_always_lock_free == 0`). Note this is an *implementation detail*.

**When do I still need a mutex, then?** `atomic` makes **one operation on one variable** indivisible. I need a mutex when atomicity has to span **more than one operation** or **more than one variable**:
- Compound op: `if (a > 0) a--;` — the load *and* the store are each atomic, but the **check-then-decrement as a pair is not** (another thread can slip in between). Fix = a mutex, or a single `compare_exchange` RMW loop.
- A whole data structure with invariants (like my goose message queue: `front()` **then** `pop()` must be one unit) → **mutex**, not atomic.

**Goose tie-in:** that's exactly why my queue is mutex-protected, not atomic — the queue ops must happen together.

## Waiting for Events

The simplest form of waiting would be an explicit sleep:

```cpp
using namespace chrono;
this_thread::sleep_for(milliseconds{20});
```

This is generally a bad approach (polling / guessing at timing). Instead, threads can communicate using external events provided by `condition_variable` in `<condition_variable>`:

```cpp
class Message { /* ... */ };

queue<Message> mqueue;        // the queue of messages
condition_variable mcond;     // the variable communicating events
mutex mmutex;                 // for synchronizing access

void consumer() {
    while (true) {
        unique_lock lck {mmutex};                         // acquire mmutex
        mcond.wait(lck, []{ return !mqueue.empty(); });   // release mmutex & wait;
                                                          // re-acquire on wakeup;
                                                          // don't wake up unless non-empty
        auto m = mqueue.front();                          // get the message
        mqueue.pop();
        lck.unlock();                                     // release mmutex
        // ... process m ...
    }
}

void producer() {
    while (true) {
        Message m;
        // ... fill the message ...
        scoped_lock lck {mmutex};   // protect operations
        mqueue.push(m);
        mcond.notify_one();         // notify
    }                               // release mmutex at end of scope
}
```

Notice the consumer uses **`unique_lock`**. A `scoped_lock` cannot be moved and has no `unlock()`, but a `unique_lock` can be unlocked/relocked — which is exactly what `wait()` needs (it *unlocks* while sleeping and *re-locks* on wakeup). The producer can use `scoped_lock`, since it just locks/unlocks over a defined scope via RAII.

**Note to self — the predicate is not optional.** `mcond.wait(lck, pred)` is the *predicate* form, and it's the right one: it re-checks `pred` on every wakeup, so it swallows **spurious wakeups** *and* the **lost-wakeup** race (if the queue was already non-empty, it doesn't wait at all). The bare `wait(lck)` (no predicate) is the footgun.

## Communicating Tasks

The standard library provides higher-level facilities for tasks (all in `<future>`):
* `future` and `promise` — for returning a value from a task on a separate thread.
* `packaged_task` — to help launch tasks and wire up the return-a-result mechanism.
* `async()` — for launching a task in a manner very similar to a plain function call.

### `future` and `promise`

`future` and `promise` allow the transfer of a value between tasks **without explicit use of a lock**.

When a task wants to pass a value, it puts the value into a `promise`. The value appears in the corresponding `future`, from which it can be read:

If we have a `future<X>` we can `get()` the value:

```cpp
X v = fx.get();   // if necessary, wait for the value to be computed
```

This blocks until the value arrives. If the value can't be computed, `get()` **rethrows** the exception that the producer stored:

```cpp
void f(promise<X>& px) {                       // a task: place the result in px
    try {
        X res;
        // ... compute a value for res ...
        px.set_value(res);
    }
    catch (...) {                              // oops: couldn't compute res
        px.set_exception(current_exception()); // pass the exception to the future's thread
    }
}

void g(future<X>& fx) {                         // a task: get the result from fx
    try {
        X v = fx.get();   // if necessary, wait for the value
        // ... use v ...
    }
    catch (...) {         // oops: someone couldn't compute v
        // ... handle error ...
    }
}
```

**How are the future and the promise created?** You make the **promise** first, then mint the **future** from it with `get_future()`:

```cpp
promise<X> px;                      // create the promise (producer end)
future<X> fx = px.get_future();     // the future is minted FROM the promise (consumer end)
// hand px to the worker thread; keep fx in the caller
```

They share a hidden "shared state." The promise is the producer end (`set_value`/`set_exception`); the future is the consumer end (`get`). `get_future()` wires them together. (With `async` I never make either — it returns the future. With `packaged_task`, I call `pt.get_future()`.)

### `packaged_task`

`packaged_task` simplifies setting up tasks connected with `future`s and `promise`s to be run on `thread`s. It provides wrapper code to put the task's return value into a `promise`. Example: two tasks each summing half of a `vector<double>` via `accumulate()`:

```cpp
double accum(vector<double>::iterator beg, vector<double>::iterator end, double init) {
    // sum of [beg:end) starting from init
    return accumulate(&*beg, &*end, init);
}

double comp2(vector<double>& v) {
    packaged_task pt0 {accum};              // package the task (accum)
    packaged_task pt1 {accum};
    future<double> f0 {pt0.get_future()};   // grab pt0's future
    future<double> f1 {pt1.get_future()};   // grab pt1's future
    double* first = &v[0];
    thread t1 {move(pt0), first, first + v.size()/2, 0};          // start a thread for pt0
    thread t2 {move(pt1), first + v.size()/2, first + v.size(), 0};
    // ...
    return f0.get() + f1.get();             // get the results
}
```

Note the `packaged_task` must be **moved** (not copied) — it's a resource handle for its `promise` and the resources its task may own.

### `async()`

> `async()` separates the "call part" of a function call from the "get the result part," and separates both from the actual execution of the task. Using `async()`, you don't have to think about threads and locks — you think in terms of tasks that potentially compute their results asynchronously. Obvious limitation: don't even think of using `async()` for tasks that share resources needing locking.

**So what does `async()` provide that isn't provided by `packaged_task`?**

Both hand me a `future`. The difference is **who launches the thread**:
- **`packaged_task`** — *I* launch it. Wrap the callable, grab its future, then **I** start a `thread` (or hand it to my own pool) and `move` the task onto it, and join. → use when I want to control **where/how/when** it runs.
- **`async`** — launches for me. `async(launch::async, f, args)` creates the thread, runs `f`, wires the future, hands it back. I never touch a `thread` object. → use when I just want **"the result, later."**

So `async` = `packaged_task` + thread-management, bundled. `packaged_task` is the middle layer for when *I* own the scheduling. (The book's `comp2` used `packaged_task` because it hand-spawned `t1`/`t2`; with `async` it'd just be `auto f0 = async(accum, …); auto f1 = async(accum, …); return f0.get() + f1.get();` — no explicit threads.)

### Stopping a thread

Sometimes we need to stop a thread because we no longer want its result. We don't want to *kill* it — it may own resources that must be released. Instead, a `stop_token` tells a thread to terminate cooperatively; the thread polls it:

```cpp
void fn(stop_token tok) {
    while (!tok.stop_requested()) {
        // ...
    }
}
```

And the caller requests a stop:

```cpp
stop_source ss1 {};
jthread t1 {fn, ss1.get_token()};

while (result == -1)
    this_thread::sleep_for(10ms);

ss1.request_stop();
```

**This seems like it could be handled with an atomic_bool.**

However, `stop_token` is the **standardized, composable** version of exactly that atomic-bool pattern. What it buys over a hand-rolled `atomic<bool>`:
1. **`jthread` integrates it** — `jthread`'s destructor calls `request_stop()` then `join()`. Cooperative cancellation wired into the RAII thread type for free. A raw `atomic<bool>` doesn't hook into that.
2. **It can cancel a *blocked* thread** (the big one): a plain `atomic<bool>` **can't wake a thread parked in a condvar `wait`**. But `condition_variable_any::wait(lock, stop_token, pred)` wakes on a stop request. (`std::stop_callback` also runs a function on stop.)
3. **Clean ownership split:** `stop_source` (who *can* request) vs `stop_token` (who *observes*), shareable across many tokens.

For a simple **polling** loop, `atomic<bool>` really is equivalent — my instinct was fine. `stop_token` earns its keep when I want `jthread`'s auto-cancellation, or when I need to cancel a thread **blocked on a condvar**. 

## Coroutines

A coroutine is essentially a function that **saves its state between calls** — its locals and *where it suspended* — so it can resume where it left off. It saves its state in a **coroutine frame** (typically heap-allocated), not a stack frame — that's *why* it can outlive a normal call and resume.

`co_yield` returns a value and suspends (waits for the next call). `co_return` returns a value and terminates the coroutine. (`co_await` suspends until an awaited thing is ready.)

The language features of coroutines (`co_await`/`co_yield`/`co_return` + the `promise_type` machinery) are in C++20. However, C++20 has no ready-made `generator`/`task` types, just the low-level `coroutine_handle`. That's why people reached for **Cppcoro**.

`std::generator` landed in **C++23**.

### Cooperative Multitasking

Consider a system with many tasks that are actors each performing a small part of a large effort.

One way to handle this is with threads — but each thread costs several megabytes for its stack, so this doesn't scale to *many* tasks.

An alternative: tasks that communicate through **message queues**. A task places itself on an event queue to wait for more work after producing a result; a **scheduler** picks the next runnable task from the queue. This is **cooperative multitasking**.

We can build it starting from a polymorphic event type:

```cpp
struct Event_base {
    virtual void operator()() = 0;
    virtual ~Event_base() {}
};

template<class Act>
struct Event : Event_base {
    Event(const string n, Act a) : name{n}, act{move(a)} {}
    string name;
    Act act;
    void operator()() override { act(); }
};
```
